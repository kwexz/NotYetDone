## Что забрать по приоритету

### 1. Счётчик tool-событий как признак стагнации — `untildone`

Агент может «работать» без единого вызова инструмента: модель печатает текст
вместо действия. Именно из этого родился `untildone`.

У нас сигнал только digest checklist. Если файл не менялся три раза — цикл
останавливается, но это грубая эвристика: агент мог честно исследовать код.

**Идея:** считать tool-события между двумя `execution.succeeded`. Ноль
инструментов + неизменный digest = стагнация, а не прогресс.

### 2. Детерминированный гейт завершения — `until-done`, `untildone`

`until-done` требует, чтобы критерий был командой с кодом возврата 0, либо
цитатой вывода инструмента. `untildone` имеет `--check 'npm test'`.

У нас галочка в Markdown. Это слабее всего в текущей реализации.

**Идея:** необязательный `check` в состоянии — команда, которую плагин
запускает сам после успешного исполнения, и продолжает только при коде 0.
Требует явного согласия пользователя: это исполнение кода.

### 3. Восстановление после compaction — `until-done`

Cursor/Claude теряют skill из контекста при сжатии. `until-done` ставит
SessionStart hook, который возвращает goal после compaction или resume.

**Идея:** при `session.compacted` переотправлять состояние задачи, если
контроль включён. Проверить, есть ли такое событие в V2.

### 4. `resume` по сохранённому состоянию — `untildone`

У нас после остановки нужно вручную просить `enable`. У `untildone` —
`resume <run-id>` с сохранёнными итерациями и счётчиками.

**Идея:** `action=resume` без сброса счётчиков, отдельно от `enable`.

### 5. Явное `blocked_external` как терминальное состояние — `until-done`, OMO

`until-done` различает DONE и BLOCKED и требует закончить всё, что не зависит
от ответа человека, прежде чем спрашивать. OMO исключает blocked-todos из
счётчика незавершённых, иначе цикл бесконечен.

У нас `block` отключает контроль с причиной, но это не отдельное состояние:
нельзя отличить «заблокировано» от «пауза».

**Идея:** `status` должен показывать `blocked_external` с причиной и списком
того, что уже сделано.

### 6. Один общий stop для всех путей — OMO PR #6039

Дефект OMO: stop работал только в одном entry point, остальные продолжали
цикл. Урок: остановка — это состояние и приоритет, а не распознавание одной
фразы.

У нас stop ловится в prompt hook по префиксу. Если клиент отправит stop иначе
(кнопкой, командой), он не сработает.

**Идея:** проверять stop-state непосредственно перед отправкой prompt, а не
только в момент ввода.

### 7. Контракт с approval до начала работы — `pi-until-done`

`pi-until-done` сначала формирует контракт цели и план, показывает
пользователю и ждёт `/until-done approve`. Только потом работает.

**Идея:** для длинных задач полезно; для нас — избыточно, пока задача уже
описана в checklist.

### 8. «Доверяй артефактам, а не словам» — `finish-him`

Формулировка и правило: «почти готово» не существует; нужен коммит, ссылка или
скриншот. Это не механизм, но хорошая формулировка для prompt и документации.

## Что сознательно не берём

- **Внешний процесс и дочерние сессии.** Другой режим, другая стоимость.
- **Обязательный LLM-судья.** Второй агент в цикле, ключи, деньги. Вернуться
  только если гейта по команде окажется недостаточно.
- **Собственный фазовый автомат** (RED/GREEN/REFACTOR). Навязывает методологию;
  checklist уже описывает порядок.
- **Обязательный `mise`/Python-инсталлятор.** Лишняя зависимость.

## Чего у нас нет и почему это нормально

- Нет кроссплатформенных адаптеров — ядро ещё не доказано.
- Нет публикации — см. D9 в `DECISIONS.md`.
- Нет телеметрии и сетевых вызовов — сознательно.

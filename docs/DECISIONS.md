# Решения

Каждое решение — с причиной и границей применимости. Отменять только явно,
новым решением, а не молчаливой правкой кода.

## D1. Внутрисессионный плагин, не внешний супервизор

OpenCode V2 даёт `ctx.event.subscribe` и `ctx.session.prompt` внутри той же
сессии. Внешний супервизор (`untildone`, Ralph) требует отдельного процесса,
дочерних сессий, своих логов и ключей. Для интерактивного чата это другой
режим работы, а не улучшение.

**Граница:** если понадобится работа при закрытом OpenCode — это отдельный
продукт, не этот плагин.

## D2. Opt-in на сессию и на конкретный файл

В новой сессии контроль выключен. Включается только явной просьбой и только
для указанного Markdown-checklist. Иначе обычные вопросы и обсуждения
превращаются в самопроизвольную реализацию.

## D3. Продолжение только по `session.execution.succeeded`

`interrupted` и `failed` отключают контроль до явного включения. Пользователь
должен иметь возможность остановить работу одним словом.

## D4. Идемпотентность по идентификатору события

События в V2 durable и несут `id` (fallback `durable.aggregateID:seq`).
Идентификатор запоминается в памяти и в plugin storage (`lastEventID`), поэтому
повторная доставка после reconnect или перезагрузки плагина не даёт второй
prompt.

**Почему:** наблюдался лишний prompt после уже закрытого checklist. Причина не
была доказана журналом, поэтому исправление сделано как идемпотентность —
корректное свойство независимо от причины.

**Граница:** если runtime начнёт доставлять одно и то же исполнение с разными
id, эта защита не сработает. Тогда нужен content-hash или execution id.

## D5. Лимиты вместо бесконечного цикла

12 продолжений и 3 повтора с неизменным digest checklist. Это ограничение
расходов, а не доказательство прогресса.

## D6. Пока без LLM-судьи

`untildone` и `pi-until-done` проверяют завершение отдельной моделью. Это
дороже, требует ключа и добавляет второго агента в цикл. Сейчас завершение
определяется checklist и отчётом агента.

**Граница:** это слабое место. Возвращаться к судье или к детерминированному
гейту (`--check`) — см. ROADMAP, фаза 2.

## D7. Никаких команд из task-файлов

Плагин не исполняет произвольные команды, найденные в Markdown. Иначе
task-файл становится вектором выполнения кода.

## D8. Имя: NotYetDone

Проверены GitHub-репозиторий под `kwexz`, npm, PyPI, scoped-пакет — на
2026-10-28 свободны; в поиске GitHub практически нет одноимённых проектов.
Отклонены: Taskline (org и npm заняты), Continuum (занято), Taskwarden
(четыре task-manager проекта и два коммерческих сервиса), Proofline (npm, PyPI
и `sfayka/Proofline` заняты тем же смыслом), Until-done (npm занят,
`TameTheGame/until-done` — та же задача), Finish-him (цитата Mortal Kombat +
одноимённый agent skill), Dontstopper (свободно, но нечитаемо).

Подробности: `docs/research/naming.md`.

## D9. Не публиковать до доказанной ниши

Аналоги закрывают идею. Уникальность сейчас — только рантайм: в OpenCode V2
нет работающего continuation (V2-entrypoint OMO — заглушка). Это упаковка под
один рантайм, а не новая идея.

**Условие публикации:** живой smoke, отсутствие дублей, и конкретный сценарий,
который не закрывают `untildone`, `until-done`, `pi-until-done` и `Proofline`.

## D10. Только OpenCode V2

V1-плагины не работают в V2 без портирования. Адаптеры для других агентов —
после того, как ядро доказано, и только как отдельные пакеты.

## D11. MIT

Совместимо с экосистемой плагинов и не мешает использовать код в других
агентах.

## D12. Windows-first

Проверенная платформа — Windows. `untildone` на Windows не работает вообще
(spawn ENOENT/EINVAL, отсутствие `sh`). Для нас это одновременно ограничение
и преимущество, которое нельзя терять.

## D16. Оставить личным инструментом

Решение 2026-10-29: не публиковать. Сценарий Windows/OpenCode V2 без
внешнего judge key проверен, но POSIX-сравнение ограничено тестами аналога
(51/52, модельный прогон not-run), а macOS smoke отсутствует. Это не основание
объявлять превосходство или выпускать пакет. D9 сохраняется: публикация,
тег и push требуют отдельной просьбы пользователя.

## D17. Другие адаптеры — только после приёмки 0–5

См. docs/ROADMAP.md. Новый адаптер оформляется отдельным change и пакетом,
не вторым владельцем продолжения. Реализация Claude Code в этом change
не начинается. policy.mjs остаётся независимым от OpenCode.

## D13. Один владелец продолжения в процессе

По явному согласованию с пользователем критерий одной строки loading plugin
заменён поведенческим: один владелец, один prompt на событие, сохранённые
tool registrations каждого контекста. Число загрузок не равно числу владельцев.

Активная подписка на события хранится в
`globalThis[Symbol.for('notyetdone.owner')]`. Повторный `setup` сначала
освобождает предыдущего владельца, затем регистрирует себя. Плагин не пытается
запретить повторную загрузку через настройки пользователя.

Уточнение: замена владельца отменяет только его event loop и активные
проверки (`deactivate`), но не удаляет tool transforms и hooks из другого
контекста OpenCode. Полная очистка регистраций выполняется при настоящем
dispose соответствующего контекста. Иначе очередной setup удаляет инструмент
из уже открытой сессии. Продолжение по-прежнему имеет одного владельца.

**Почему:** живой smoke 2026-10-29 показал четыре `loading plugin` без парных
`dispose` в одном процессе и четыре prompt на одно событие. Все экземпляры
делят `globalThis`, поэтому реестр устраняет наблюдённую причину
детерминированно.

**Граница:** реестр действует внутри одного процесса. Для нескольких процессов
остаётся best-effort `ownerToken` в storage и диагностика в `status`; атомарной
блокировки между процессами нет.

## D14. Отмена очереди: пометка всегда, отзыв — по факту API

`pause`/`stop`/`block` переводят контроль в неактивное состояние и помечают
`pendingPrompt.cancelled` с причиной. Отзыв уже поставленного сообщения
выполняется только если в рантайме реально есть `ctx.session.inbox.cancel`;
идентификатор берётся из результата `session.prompt` (`SessionInbox.User.id`).
Результат попытки (`ok`/`reason`) пишется в состояние и виден в `status`.

**Почему:** в клиентском API V2 метод `session.inbox.cancel` есть, но контекст
плагина типизирован как `Pick<SessionApi, ...>` без `inbox`. Обещать отзыв,
которого может не быть на объекте, нельзя.

**Граница:** если рантайм не отдаёт `inbox`, уже поставленный prompt может
доставиться после паузы; новые prompt не ставятся. Это остаточный риск, а не
`blocked_external`: платформа умеет отзывать, ограничение — в поверхности
плагина. Evidence: `state/STATUS.md`, «Проверка 1.5».

## D15. Opt-in гейт проверки

Пользователь может передать `check` при `task_continuity action=enable`:
`{file, args, cwd, timeoutMs, maxOutput}`. Запуск — только по этому явному
вводу в инструмент, только пока сессия активна. `check` принимается
исключительно вместе с `enable`; для `pause`, `status` и `block` он отклоняется.

**D7 не отменяется.** Плагин по-прежнему не читает команды из Markdown,
не парсит task-файл на предмет «что запустить» и не выполняет ничего из
содержимого checklist. Гейт — это отдельный аргумент инструмента, который
пользователь (или агент по его прямой просьбе) передаёт один раз при включении.

**Запуск:** `spawn(file, args, {cwd, shell:false})`. `file` — имя в `PATH` или
путь внутри проекта; абсолютные пути и выход за проект отклоняются. `cwd` —
внутри проекта. Таймаут по умолчанию 120 с (100 мс … 600 с), лимит вывода
8 000 символов (200 … 64 000); при превышении хранится хвост, потому что
продолжению нужен конец вывода, а не начало. При таймауте процесс убивается.

**Семантика:** код 0 — `Gate check passed`, цикл останавливается, даже если
чекбоксы не закрыты. Любой другой исход (ненулевой код, таймаут, ошибка
запуска) — цикл продолжается, хвост вывода добавляется к следующему prompt.
Закрытый checklist при настроенном `check` больше не завершает цикл сам по
себе: считать закрытые чекбоксы доказательством нельзя. Счётчики `runs`,
`unchanged`, `idleTools` при этом продолжают действовать, поэтому «вечно
красная» проверка упирается в тот же предохранитель.

**Windows:** `.exe` запускается напрямую без shell. `.cmd`/`.bat` отклоняются:
для них нужен shell. Для JS-проверки укажите `file: "node"` и путь к скрипту
в `args`; не используйте `npm.cmd` или `cmd.exe` как обход этого ограничения.

**Граница:** гейт не доказывает корректность самого скрипта проверки, не
изолирует его (нет sandbox, сети и прав), не кэширует результат и не
запускается по таймеру — только после успешного исполнения сессии.

# Design

## Context

См. `proposal.md` — Why. Текущее устройство, которое определяет подход:

- Один вход `index.mjs` (`Plugin.define`), чистая логика в `policy.mjs`,
  тесты через `node --test` с фейковым `ctx`.
- Доступный API V2: `ctx.event.subscribe`, `ctx.session.prompt`,
  `ctx.session.hook`, `ctx.storage`, `ctx.tool.transform`, `ctx.session.get`.
- Состояние живёт в plugin storage по ключу `session:<id>`; события
  живые, без replay из БД.
- Живой прогон 2026-10-29: четыре `loading plugin` в одном процессе без
  парных `dispose`, одно событие → четыре prompt.
- Ограничения проекта: один владелец продолжения; stop/interrupt важнее
  успеха; отмена покрывает callbacks, таймеры и очередь; без телеметрии,
  сети и внешних ключей; Windows-first; команды из task-файлов запрещены.

## Goals / Non-Goals

**Goals:**

- Детерминированно получать один prompt на одно успешное исполнение.
- Сделать остановку действующей на всё, что ещё может продолжить работу.
- Добавить счётчики стагнации, opt-in гейт, состояния и resume без сброса.
- Оставить поведение проверяемым unit-тестами и одним живым smoke.

**Non-Goals:**

- Новые рантаймы и адаптеры (фаза 6).
- LLM-судья и любые сетевые проверки.
- Публикация, тег, push.
- Изменение модели, permissions и кода проекта пользователя.

## Decisions

### D-A. Один владелец через process-global registry

`setup` регистрирует владельца в `globalThis[Symbol.for('notyetdone.owner')]`
как объект с `abort`/`dispose`. Если владелец уже есть, новый `setup` сначала
освобождает его, затем регистрирует себя.

Почему: все четыре наблюдённые загрузки были в одном процессе, а `globalThis`
разделяется всеми экземплярами модуля в этом процессе. Это устраняет
наблюдённую причину детерминированно.

Альтернативы: lease в storage (нужен для нескольких процессов, но остаётся
read-then-write и не помогает в одном процессе); запрет повторной загрузки
через конфиг (не наша зона — плагин не меняет настройки пользователя).

Для нескольких процессов добавляется best-effort `ownerToken` в storage:
экземпляр пишет токен и перечитывает его перед постановкой prompt. Токен не
даёт атомарности; он только сужает окно и делает гонку видимой в `status`.

### D-B. Claim до prompt, а не после

Порядок обработки успеха:

1. Прочитать состояние и проверить `lastEventID`.
2. Записать `lastEventID`, `pendingPrompt = {eventID, token}` и счётчики.
3. Только после успешной записи вызвать `ctx.session.prompt`.

Повторная обработка того же события увидит `lastEventID` и `pendingPrompt` и
не поставит второй prompt. `execution.started` очищает `pendingPrompt`, то есть
подтверждает, что предыдущий prompt был потреблён.

Альтернатива: ставить prompt и потом писать состояние — именно этот порядок
даёт окно, в котором дубль проходит.

### D-C. Отмена очереди: сначала проверить API, потом обещать

`pause`/`stop`/`block` переводят состояние в неактивное и помечают
`pendingPrompt.cancelled = true`. Если V2 отдаёт идентификатор сообщения и
операцию отзыва, плагин отзывает его. Если нет — это фиксируется как
`blocked_external` с evidence, а prompt получает первым шагом проверку
`task_continuity status`.

Почему не «просто не ставить новые»: инвариант проекта требует покрывать уже
поставленные prompt. Обещать отзыв без проверки API нельзя.

### D-D. Claim связан с событием, а не с глобальной очередью

`pendingPrompt` хранит `{eventID, token, inboxID, cancelled}` и служит
наблюдаемости и защите от повторной постановки **того же** события. Это не
глобальный lock: два разных успешных исполнения законно дают два продолжения.
Запрет ставить второй prompt, пока первый не потреблён, ломает сценарий, где
runtime не присылает `execution.started` для уже доставленного сообщения, и
был отброшен после теста `distinct executions still continue...`.

От накопления очереди защищают: один владелец (D-A), claim по `event.id`
(D-B) и очистка claim по `execution.started`.

### D-E. Стагнация: два разных сигнала

- `unchanged`: digest checklist не изменился между успешными исполнениями.
- `idleTools`: между успешными исполнениями не было tool-событий.

Остановка по стагнации — при `unchanged >= 3` (уже есть) или
`idleTools >= 2` при неизменном digest. Порог 2, а не 1: правки только в
документации без инструментов возможны, но два холостых прогона подряд — уже
сигнал.

Имена tool-событий V2 неизвестны и проверяются research-задачей. Если
подходящего события нет, счётчик остаётся `null`, а `status` честно показывает
`not-run`, а не ноль.

### D-F. Гейт: команда как данные, не как shell-строка

Состояние получает `check: {file, args, cwd, timeoutMs, maxOutput}`. Запуск —
через `spawn(file, args, {cwd, timeout, signal})`, без `shell: true` и без
конкатенации строк. Это исключает подстановку команд из Markdown и снимает
зависимость от `sh` на Windows.

Источник — только явный вызов `task_continuity` пользователем. Нужно новое
решение `D15`, которое фиксирует: D7 запрещает команды из task-файлов, а
opt-in гейт допустим только как явный ввод и с согласием.

Семантика: код 0 → `gate_passed` и остановка; ненулевой код → продолжение с
хвостом вывода в пределах лимитов. Таймаут и превышение вывода — неуспех.

### D-G. Фаза как единственный источник статуса

В состояние добавляется `phase`: `active` | `paused` | `blocked_external` |
`complete` | `limit` | `error` | `gate_passed`. Поле `enabled` остаётся для
совместимости, но `status` строится по `phase`.

Старые записи без `phase` читаются через вывод из `enabled`/`reason`, без
миграции данных.

### D-H. Compaction: восстановление, а не новый prompt

Если V2 даёт событие компакции, плагин сохраняет краткую сводку состояния и
добавляет её к следующему продолжению, не порождая отдельный prompt. Если
события нет — `not-run` с описанием проверки.

### D-I. Ядро политики отдельно от адаптера

`policy.mjs` остаётся чистым и не знает про OpenCode. Новые правила (стагнация,
phase, лимиты) добавляются туда и тестируются без фейкового `ctx`. Это же
подготовит фазу 6, но адаптеры в этот change не входят.

## Risks / Trade-offs

- [Global registry не покрывает несколько процессов] → best-effort
  `ownerToken` в storage, `status` показывает владельца, живой smoke фиксирует
  число `loading plugin`.
- [API не даёт отозвать очередь] → честный `blocked_external` с evidence;
  ограничение попадает в `STATUS.md`, а не в «исправлено».
- [Порог стагнации останавливает полезную работу] → порог 2, причина видна в
  `status`, `resume` не сбрасывает счётчики, но позволяет продолжить.
- [Гейт исполняет пользовательскую команду] → только явный ввод, `spawn` без
  shell, таймаут, лимит вывода, наследование окружения ограничено.
- [Compaction-события может не быть] → `not-run`, без имитации.
- [Рост `policy.mjs`] → правила остаются чистыми функциями с тестами.

## Migration Plan

1. Остановить контроль в активных сессиях (`pause`), чтобы деплой не совпал с
   уже поставленным prompt.
2. `npm ci && npm test && npm run check`.
3. `pwsh -NoProfile -File scripts/install.ps1`, перезапуск OpenCode.
4. Проверить в журнале ровно один `loading plugin` для `task-continuity`.
5. Живой smoke по `state/SMOKE.md`; evidence в `state/STATUS.md`.

Откат: сохранить копию текущих `index.mjs`/`policy.mjs`, вернуть её и
перезапустить OpenCode. Схема storage совместима: `phase` выводится из старых
полей.

## Open Questions

- Точные имена tool-событий в V2 и доступность счётчика — проверяется до
  реализации фазы 1; при отсутствии поведение остаётся `not-run`.
- Есть ли в V2 отзыв сообщения из `session_inbox` — проверяется до реализации
  отмены очереди; ответ меняет только способ отмены, не спецификацию.
